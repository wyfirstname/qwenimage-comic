## 1. 项目概述

### 1.1 背景

Qwen-Image 2.1 是通义千问开放的图像生成基座模型（7B 参数量，`qwen_image21` 架构），支持文生图、图片编辑、透明背景、多参考图。社区（原发者 `abenzerps`）发布了它的 **GGUF 量化 + 去安全检查器** 版本，可在消费级显卡本地跑。

### 1.2 为什么自建（对比当前方案）

当前项目走 SiliconFlow 的 `Qwen/Qwen-Image-Edit-2509` 在线 API。自建本地版的价值：

| 维度 | 在线 API | 本地 GGUF 自建 |
|---|---|---|
| 费用 | 按次计费 | 一次性硬件 / 电费 |
| 隐私 | 图片与提示词上传第三方 | 全离线，数据不出本机 |
| 内容限制 | 平台审核策略 | 无内置检查器，策略自定 |
| 延迟稳定性 | 受网络与排队影响 | 本地稳定，首次加载慢 |
| 并发 | 受 API 配额限制 | 受显存限制，通常串行 |
| 出图风格 | 服务端固定 | 可自定义工作流 / LoRA / ControlNet |
| 运维 | 无需维护 | 需维护环境与显存调度 |

**结论**：本地版适合「隐私敏感 + 高频次 + 需要自由工作流」的场景；如果只是偶尔出图，保留在线 API 作为兜底更划算。本方案设计为**双通道可切换**。

### 1.3 核心目标

- 本地加载 `qwen-image-2.1-UC` GGUF 模型，完成文生图与图生图编辑
- 提供 REST API，支持同步出图与异步任务队列
- 提供 Web UI：提示词输入、参数调节、图库管理、批量任务
- 支持 LoRA、ControlNet 等可选扩展
- 内置 NSFW 内容标记（由**使用者**自行决定是否启用）

### 1.4 非目标

- 不做在线多租户服务（本地单用户 / 内网使用为主）
- 不提供模型训练 / 微调能力

## 3. 环境与硬件要求

### 3.1 硬件门槛

| 量化档 | 扩散模型 | 建议显存 | 适用显卡 |
|---|---|---|---|
| Q4_0 | 4.15 GB | 8 GB | RTX 3060 Ti / 4060 |
| **Q4_K_M（推荐）** | **4.60 GB** | **8–12 GB** | RTX 3060 12G / 4060 Ti 16G |
| Q5_K_M | 5.22 GB | 12 GB | RTX 4070 / 3080 |
| Q6_K | 5.88 GB | 12–16 GB | RTX 4070 Ti / 4080 |
| Q8_0 | 7.59 GB | 16 GB+ | RTX 4080 / 4090 |

> ⚠️ **Q8_0 存在已知问题**：ComfyUI 采样时可能出现张量尺寸不匹配。建议用 Q4_K_M / Q5_K_M / Q6_K（社区已验证）。
>
> **注意**：上述只是**扩散模型**体积。还需文本编码器（INT8 ≈ 9.35 GB，BF16 ≈ 17.53 GB）+ VAE（0.68 GB）。省显存方案：扩散模型驻显存，文本编码器驻系统内存（CPU 跑一次编码即可）。

### 3.2 软件环境

- OS：Windows 10/11（本机）、或 Linux
- Python 3.10 ~ 3.12（**不建议 3.13**：部分推理库 wheel 未就绪）
- CUDA 12.1+ / 对应显卡驱动（NVIDIA）
- 磁盘：预留 **40 GB**（模型 + 缓存 + 输出图）
- 内存：建议 32 GB（文本编码器 CPU 运行）

### 3.3 关于是否必须装 ComfyUI

社区资料默认走 ComfyUI + ComfyUI-GGUF。但**自建服务有两种路线**：

| 路线 | 说明 | 推荐度 |
|---|---|---|
| **A. Python 直连推理** | 用 `diffusers` + GGUF 加载器，在 Python 进程内直接跑推理，自建 API | ⭐ 推荐，易集成、无需额外进程 |
| **B. ComfyUI 作为推理引擎** | 自建 API 通过 ComfyUI 的 `/prompt` HTTP 接口提交工作流 | 适合已熟悉 ComfyUI、需要复杂节点工作流 |

本文档以 **路线 A** 为主，路线 B 作为附录方案。

## 5. 推理后端设计

### 5.1 模型生命周期

```
启动 → 不加载模型（懒加载）
   ↓
首个请求 → 加载 Transformer / TextEncoder / VAE 到对应设备
   ↓
常驻（默认）── 空闲超时（可配，如 30 分钟）→ 卸载，释放显存
```

配置项：

```yaml
model:
  device: cuda:0
  transformer_dtype: fp16
  text_encoder_dtype: int8
  text_encoder_device: cpu        # 省显存关键：文本编码器放 CPU
  keep_loaded: true               # 常驻显存
  idle_unload_seconds: 1800
  vae_tiling: true                # 大图必开，防 OOM
```

### 5.2 显存守卫（VRAM Guard）

单卡推理必须串行。用一个全局异步锁 + 显存检查：

```python
# app/inference/scheduler.py
import asyncio, torch

class InferenceScheduler:
    def __init__(self):
        self._lock = asyncio.Lock()

    @staticmethod
    def free_vram_gb() -> float:
        if not torch.cuda.is_available():
            return 0.0
        free, _ = torch.cuda.mem_get_info()
        return free / 1024**3

    async def run(self, fn, *args, **kwargs):
        async with self._lock:                      # 串行化，避免并发 OOM
            if torch.cuda.is_available():
                torch.cuda.empty_cache()
                if self.free_vram_gb() < 1.0:       # 低于 1GB 触发卸载
                    await self._maybe_unload()
            return await asyncio.to_thread(fn, *args, **kwargs)
```

### 5.3 推理参数（文生图）

| 参数 | 默认值 | 说明 |
|---|---|---|
| `width` / `height` | 1024 × 1024 | 建议 1024 档；非 64 倍数会报错 |
| `steps` | 20 | 20–30 之间 ；步数越高越慢 |
| `guidance_scale` | 4.0 | Qwen-Image 系列偏低，2.5–5 通常够 |
| `seed` | 随机 | -1 表示随机 |
| `negative_prompt` | 空 | 可用 |
| `batch_size` | 1 | 显存不足时保持 1 |

### 5.4 图片编辑（img2img / 多参考图）

复用同一套权重，额外传入参考图与 `strength`：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `image` | — | 参考图（base64 或文件） |
| `strength` | 0.6 | 0=不改，1=完全重画 |
| `ref_images` | [] | 多参考图（角色一致性场景） |

## 6. 后端 API 设计

### 6.1 接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/generate` | 同步生成（阻塞返回，适合单张） |
| `POST` | `/api/v1/jobs` | 提交异步任务，立即返回 `job_id` |
| `GET` | `/api/v1/jobs/{job_id}` | 查询任务状态 / 结果 |
| `GET` | `/api/v1/jobs/{job_id}/events` | SSE 流式进度 |
| `DELETE` | `/api/v1/jobs/{job_id}` | 取消任务 |
| `POST` | `/api/v1/edit` | 图片编辑（img2img / 多参考图） |
| `GET` | `/api/v1/gallery` | 图库列表（分页 / 筛选） |
| `DELETE` | `/api/v1/gallery/{image_id}` | 删除图片 |
| `GET` | `/api/v1/models/status` | 模型加载状态、显存占用 |
| `POST` | `/api/v1/models/load` | 手动加载 / 卸载 |
| `GET` | `/api/v1/system/health` | 健康检查 |
| `GET` | `/api/v1/system/config` | 读取生效配置 |

### 6.3 错误码约定

| HTTP | code | 含义 |
|---|---|---|
| 400 | `INVALID_PARAMS` | 参数非法（尺寸非 64 倍数等） |
| 409 | `BUSY` | 推理队列已满 |
| 422 | `MODEL_NOT_LOADED` | 模型未加载且加载失败 |
| 500 | `INFERENCE_ERROR` | 推理异常（附 traceback_id） |
| 503 | `OOM` | 显存不足，建议降低分辨率/量化档 |
| 504 | `TIMEOUT` | 单次推理超时 |

### 6.4 任务队列

- 轻量场景：`asyncio.Queue` + 单 worker 协程（够用）
- 需持久化 / 重试：Celery + Redis，或 `arq`
- 任务元数据落 SQLite：

```sql
CREATE TABLE jobs (
  id           TEXT PRIMARY KEY,
  status       TEXT NOT NULL,        -- queued|running|succeeded|failed|canceled
  prompt       TEXT NOT NULL,
  negative     TEXT,
  params_json  TEXT NOT NULL,
  seed         INTEGER,
  created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
  started_at   DATETIME,
  finished_at  DATETIME,
  error        TEXT
);

CREATE TABLE images (
  id          TEXT PRIMARY KEY,
  job_id      TEXT REFERENCES jobs(id),
  path        TEXT NOT NULL,
  width       INTEGER, height INTEGER,
  seed        INTEGER,
  prompt      TEXT,
  nsfw_score  REAL,                  -- 可选：敏感度打分
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_images_job ON images(job_id);
CREATE INDEX idx_images_created ON images(created_at DESC);
```

### 7.3 关键交互

1. **参数预设**：快速切换「快速预览（1024×1024/12步）」与「高质量（1536×1536/30步）」
2. **种子锁**：锁定 seed 后微调提示词做对比实验
3. **图片详情侧栏**：展示完整参数，支持「复现此图」「以此图继续编辑」
4. **拖拽参考图**：主画布拖入图片 → 自动进入编辑模式
5. **批量任务**：提示词支持按行解析，一次提交多条

### 7.4 若沿用 Electron 客户端

现有 Electron 壳可直接复用：

- 主进程：负责启动/守护本地 Python 后端进程（`child_process.spawn`），并在退出时清理
- 渲染进程：直接指向 `http://127.0.0.1:8000`
- 优势：用户无需手动跑后端，双击即用
- 注意：打包时需一并分发 Python 环境或模型路径配置引导（模型体积大，建议**模型不打包**，首次运行引导用户选择模型目录）

### 10.2 模型管理器（懒加载 + 卸载）

```python
# backend/app/inference/loader.py
import torch, gc
from loguru import logger

class ModelManager:
    def __init__(self, settings):
        self.s = settings
        self._loaded = False
        self.transformer = self.text_encoder = self.vae = None

    def ensure_loaded(self):
        if self._loaded:
            return
        logger.info("Loading Qwen-Image 2.1 GGUF ...")
        # 1) 加载 GGUF transformer（具体 API 取决于所用加载器，见 4.4 节三种方案）
        # 2) 加载文本编码器到 self.s.text_encoder_device（CPU）
        # 3) 加载 VAE
        self._loaded = True
        logger.info(f"Loaded. free_vram={torch.cuda.mem_get_info()[0]/1024**3:.2f}GB")

    def unload_all(self):
        for attr in ("transformer", "text_encoder", "vae"):
            setattr(self, attr, None)
        gc.collect()
        if torch.cuda.is_available():
            torch.cuda.empty_cache()
        self._loaded = False
        logger.info("Model unloaded, VRAM released.")
```

### 10.3 图生图 / 多参考图

当前架构下真正的多图通道是 **Qwen-Image 2.1 原生编辑**（ComfyUI `TextEncodeQwenImage21`），
它把参考图既送进 Qwen3-VL 视觉塔、又按序列拼进 VAE latent：

```python
# comfy_engine._build_workflow（ref_names 非空时）
nodes["12"] = g("TextEncodeQwenImage21",
                clip=["2", 0], prompt=prompt, negative_prompt=negative,
                vae=["3", 0], resolution=0,                     # 0 = 参考图保持自身尺寸
                images={"image_1": ["21", 0], "image_2": ["22", 0]})
nodes["9"] = g("KSampler", model=["4", 0],
               positive=["12", 0], negative=["12", 1],
               latent_image=["12", 2],                          # latent 必须用该节点输出
               cfg=1.0, denoise=1.0, sampler_name="euler", scheduler="simple")
```

要点（官方约定，踩坑必看）：

| 项 | 取值 | 说明 |
|---|---|---|
| latent | 节点输出的空 latent | 尺寸跟随 `image_1`；换成别的尺寸编辑会整体偏移 |
| CFG | **1.0** | 官方路径；此值下负面提示词不参与采样 |
| denoise | **1.0** | 编辑不是"部分重绘"，靠参考图 conditioning 约束 |
| resolution | 0 | 参考图保持各自尺寸（调用方已按需缩放，按 32 取整）|
| 提示词 | `image_1` / `image_2` 索引 | 例："place the character from image_2 into the scene of image_1" |

⚠️ 低去噪 img2img（`VAEEncode` + `strength<1`）不适用于"融合"：构图由参考图主导，
必然得到"只有参考图"的结果。该通道仅保留给主界面的传统图生图。

## 12. 性能调优

| 目标 | 手段 |
|---|---|
| 显存不足 | 文本编码器放 CPU；降量化档；开 `vae_tiling`；降分辨率到 768；ComfyUI 下加 `--lowvram` |
| 速度慢 | 升量化档反而不一定快；降 `steps`；开启 torch.compile / TensorRT（需适配）；固定尺寸避免重编译 |
| 首图慢 | 模型懒加载导致的首次开销；改 `KEEP_LOADED=true` 常驻 |
| 批量出图 | 用异步任务队列，避免 HTTP 长连接超时 |
| 文本编码复用 | 相同提示词缓存 embedding（进阶优化） |
| 秒级响应 | 小尺寸 + 12 步做「草稿」，满意后再跑高质量 |

**参考速度**（RTX 4070 Ti 12G，Q4_K_M，1024×1024，20 步）：约 **8–15 秒/张**，首次含加载约 1–2 分钟。实际以你的硬件为准。

## 13. 故障排查

| 现象 | 原因 | 解决 |
|---|---|---|
| `Unknown model architecture!` | 用了老版 city96 的 ComfyUI-GGUF | 换 leejet 的维护分支 |
| 张量尺寸不匹配 | Q8_0 已知缺陷 | 换 Q4_K_M / Q5_K_M / Q6_K |
| CUDA OOM | 显存不足 | 文本编码器转 CPU、降分辨率、`--lowvram`、关 tiling 反例（tiling 是开的） |
| 出图全黑 / 全灰 | 量化档过低或 VAE 不匹配 | 确认 VAE 用仓库提供版本；换 Q5_K_M |
| 提示词被拒绝 | 说明用了带检查器的版本 | 确认加载的是 `-UC`（Uncensored）权重 |
| hf 下载中断 | 网络问题 | 用 `hf-mirror.com` + `huggingface-cli` 断点续传 |
| 多 worker 显存翻倍 | uvicorn workers > 1 | 固定 `WORKERS=1` |
| 尺寸报错 | 非 64 倍数 | width/height 取 64 的整数倍（768/1024/1152/1536） |

如果选择用 ComfyUI 跑推理，后端只需做「工作流模板 + HTTP 提交」：

```python
import json, uuid, urllib.request

def submit(workflow: dict, server="127.0.0.1:8188"):
    client_id = str(uuid.uuid4())
    payload = json.dumps({"prompt": workflow, "client_id": client_id}).encode()
    req = urllib.request.Request(f"http://{server}/prompt", data=payload,
                                 headers={"Content-Type": "application/json"})
    return json.loads(urllib.request.urlopen(req).read())   # -> {"prompt_id": ...}
```

要点：
- 用 API 格式导出工作流（ComfyUI 设置里开 `Enable Dev mode Options` → `Save (API Format)`）
- 监听 WebSocket `ws://127.0.0.1:8188/ws` 拿进度与产出
- 需要装的节点：`leejet/ComfyUI-GGUF`（原生支持 Qwen-Image 2.1）+ 内置 `Unet Loader (GGUF)`
- 文件放置：

## 附录 C：漫画工作室与本地文本模型（已实现）

> 本附录记录 §14 路线图之外新增的能力，实现在 `backend/app/services/comic*.py`、
> `backend/app/api/comic.py`、`backend/app/inference/comfy_text.py` 与 `frontend/comic*.js`。

### C.1 定位

在「文生图 / 图生图」之外，增加一条**完整漫画生产流水线**，把原本散落在提示词里的人工步骤
产品化为六个前后衔接的步骤页签：

```
剧本  →  角色提取  →  场景  →  分镜  →  出图  →  排版导出
```

设计参照成熟的「短剧创作」流程（剧本写作 → 人物设计 → 场景设计 → 分镜/视频），
但**砍掉视频环节**，全部落在静态漫画上。

### C.2 全本地约束

| 环节 | 实现 | 是否联网 |
|---|---|---|
| 剧本创作 / 润色 | 本地 Qwen3-VL-8B（ComfyUI `TextGenerate`） | 否 |
| 角色提取 | 同上，严格 JSON 输出 | 否 |
| 场景提取 | 同上，严格 JSON 输出 | 否 |
| 智能分镜 | 同上，严格 JSON 输出 | 否 |
| 出图 / 场景概念图 | 本机 Qwen-Image 2.1 GGUF（ComfyUI + GGUF 节点） | 否 |
| 排版导出 | 后端 PIL 绘制（气泡 / 拟声词 / 页码） | 否 |

**不引入任何新运行时、不额外下载模型**：文本模型直接复用出图模型自带的文本编码器
`text_encoders/qwen3vl_8b_int8_convrot.safetensors`。在 ComfyUI 中它注册为
`CLIPLoader(type="qwen_image")`，其 `Qwen3VLClipModel` 自带 `generate()`，
因此可用官方 `TextGenerate` 节点直接做文本生成。

### C.3 本地文本生成的工作流

```
CLIPLoader(clip_name=qwen3vl_8b_int8_convrot.safetensors, type=qwen_image, device=default)
        │
        ▼
[PrimitiveStringMultiline(可选的 system_prompt)] ──▶ TextGenerate(…)
        │
        ▼
SaveText(filename_prefix=comic_llm/out)      ← 必须挂输出节点，否则 ComfyUI 报 prompt_no_outputs
```

要点（均为实测踩坑后固化）：

1. **`TextGenerate` 不是输出节点**，必须接一个输出节点（这里用 `SaveText`），否则 `/prompt` 直接 400。
2. **设备必须是 `device="default"`（cuda）**。`.env` 里为出图设的 `TEXT_ENCODER_DEVICE=cpu`
   会让 `generate()` 路径直接抛 `Expected a cuda device, but got: cpu`。
3. **嵌套入参用点号键**：采样参数不能写成嵌套 dict，要用
   `sampling_mode="on"` + `sampling_mode.temperature` 这种扁平点号键（ComfyUI `DynamicCombo` 的命名规则）。
4. **贪心解码优先**：角色 / 场景 / 分镜这类结构化提取传 `sampling_mode="off"`，稳定可复现；
   剧本创作与润色才开采样（`temperature≈0.6–0.85`）。
5. 结果直接从 `/history/{prompt_id}` 的 `outputs[node]["text"][0]` 取，不必读盘。

### C.4 长耗时任务模型

本机文本推理很慢（实测：短输出约 20–60 秒，225 字剧本约 3–7 分钟），因此：

* 所有 AI 步骤都走**单并发后台任务**（`services/comic_ai.py` 的 `AiTaskManager`），
  HTTP 只负责提交与轮询，不会超时、不阻塞事件循环；
* 前端提交后按 2 秒粒度轮询 `/comic/ai/tasks/{id}`，显示已用秒数，可取消；
* 超时会调用 ComfyUI `/interrupt` + 清队列，避免废任务堆积（与出图通道同一套纪律）。

### C.5 数据结构

| 表 | 说明 |
|---|---|
| `comic_projects` | 作品：标题、画风、排版、尺寸/步数/引导、`synopsis`（剧本正文） |
| `comic_characters` | 角色：name/role/gender/age/personality/appearance/outfit/background + `detail_prompt`（英文绘图细节）+ 参考图 |
| `comic_scenes` | 场景：name/location/time_of_day/atmosphere/desc + `prompt`（AI 提取的核心英文提示词，**拼装输入，前端可编辑**）+ `last_prompt`（最近一次实际使用的完整提示词，**只展示不参与拼装**）+ 独立的出图状态字段 |
| `comic_panels` | 分镜：seq/page/cell/shot/scene/dialogue/sfx + `scene_id` 关联场景 + `character_ids` + 出图状态 |
| `comic_renders` | 成品页：path/url/layout/page/width/height |

旧库通过 `db.py` 的增量迁移自动补列（`ALTER TABLE … ADD COLUMN`，缺列才加），无需手工重建。

### C.6 提示词组装顺序

分镜出图时，提示词按「画风 → 景别 → 画面描述 → 场景英文提示词 → 角色英文细节 → 文字禁令」拼接：

```
{style} 漫画, {shot 描述}, {panel.scene},
环境：{scene.prompt}
角色 {name}：{character.detail_prompt}
（禁止出现任何文字、气泡、对白、水印……）
```

因此**场景设定与角色英文设定会自动进入每一格**，这是「角色 / 场景两步」真正的价值所在：
不只是一份说明文档，而是直接参与出图。

### C.7 一句话版约定

* 剧本：一行一格；`[景别]` 前缀；`「对白」`；`[音效：轰隆]`；`第 N 页` 分页
* 规则拆格（`parse_script`）与 AI 拆镜（`generate_storyboard`）产出的数据结构完全一致，
  AI 失败时可无感回退到规则拆格


### C.8 排版导出与整部 PDF（2026-10-04）

* 排版渲染（`render_project_pages`）把分镜图拼成成品页 PNG；每点一次「生成漫画页」
  会**新增一批**成品页（旧批次保留在列表里可回看）。
* **导出整部 PDF**（`export_project_pdf`，`POST /comic/projects/{id}/export`）：
  * 直接读盘上的成品 PNG 按页码合并，**每个页码只取最新一份**——重排过多少次，
    PDF 里都不会出现重复页；
  * 一页成品都没有时先按当前设置自动排版一次（「一键导出」也能用）；
  * DPI 按页宽换算（1240px → 150dpi ≈ A4 宽），打印 / 阅读尺寸都合适；
  * PDF 落在项目目录 `outputs/comics/<项目名>_<id尾号>/`，与出图放在一起；
  * 项目详情带 `exports` 字段（扫描项目目录里的 `*.pdf`，按时间倒序），历史导出可再下载 / 删除，
    删除接口只接受本目录内的 `.pdf` 文件名（防路径穿越）。
* 回归测试：`backend/tests/test_pdf_export.py`（mock 引擎真实落盘，22 项断言）、
  `backend/tests/test_job_payload_blobs.py`（任务参数外置，见 C.9）。

### C.9 任务参数大字段外置（app/blobs.py，2026-10-04 事故修复）

**事故**：分镜融合任务把参考图编码成 base64 data URL 随 payload 落进 `jobs.params_json`，
单条任务 4~5MB，本机 jobs 表涨到 **151MB**，最终把 `app.db-wal` 写坏，
漫画模块整体报 `database disk image is malformed`。

**修复（三层）**：

1. **写库前外置**（`app/blobs.py`）：payload 里超过 4KB 的字符串抽成
   `data/blobs/<job_id>/<n>` 文件，库里只留 `@blob:<job_id>/<n>` 引用；
   `run_job` 从库里恢复参数时再展开还原，引擎拿到的 payload 与以前完全一致。
   任务结束后 `blobs.release(job_id)` 删除，启动时 `gc_all()` 清残渣。
2. **历史数据清理**（`db._shrink_oversized_job_params`，启动迁移自动执行）：
   已结束任务的参数快照里再留一份图片没有意义，超长字符串换成占位说明，
   然后 `VACUUM` + `wal_checkpoint(TRUNCATE)` 真正回收磁盘
   （WAL 模式下只 VACUUM 不检查点，主库文件不会变小）。
   本机与便携包均从 **156.8MB → 1.37MB**。
3. **损坏 WAL 的处置**：主库 `integrity_check=ok` 时，把 `-wal`/`-shm` 移出数据库目录即可恢复，
   不要对损坏的库做任何写操作。

> 教训：SQLite 里永远不要存 MB 级 base64；「VACUUM 了但文件没变小」大概率是 WAL 没检查点。

> **C.8.1 补充（跨机器拷库后导出失败）**：在另一台电脑生成的内容拷到本机后，
> 成品页记录里的绝对路径指向旧机器盘符（如 `D:\...`），导出报「成品页文件缺失」。
> 根因是 `_resolve_stored_path(path) or _resolve_stored_path(url)` 的坏路径解析结果
> 是"真值"，`or` 短路导致 URL 兜底永远不生效。修复：新增 `_resolve_existing()`
> （按候选顺序取第一个真实存在的文件）与 `_adopt_stored()`（归位 + 修记录，幂等），
> 导出与启动迁移统一走这两个入口；文件已在项目目录时只修记录、绝不复制两份。
> 回归测试：`backend/tests/test_cross_machine_db.py`。

### C.10 预览顺序 / 相对路径 / 黑白彩色导出 / 气泡字号（2026-10-04 上午）

1. **成品页预览顺序**：重排会产生多批成品页，列表按时间倒序展示导致页码倒着看。
   前端 `renderRenders` 现在每个页码只展示最新一份、按页码升序排列。
2. **素材路径全部改相对路径**（`models_util.stored_path` / `resolve_stored`）：
   `images.path`、`comic_renders.path`、`comic_characters.ref_path` 统一存 `data/...`
   posix 相对路径，整个 data 目录拷到别的电脑/盘符后无需改库；
   启动迁移 `normalize_stored_paths()` 幂等地把历史绝对路径改写掉
   （主字段找不到文件时用 URL 兜底再试；文件确实没拷过来的记录保持原样）。
   读取端（图库删除、分镜图/参考图加载）统一走 `resolve_stored`。
3. **排版不再烘焙灰度**：成品页永远保留分镜图原有色彩；导出 PDF 增加
   `color_mode`（`color` 彩色版 / `bw` 黑白版，黑白在合成时转灰度、不动原文件，
   文件名带 `_黑白版` 标识）。前端导出区改为【彩色版 / 黑白版】下拉。
4. **气泡字号**：`_draw_bubble` 系数 0.055 → 0.042，并加 26px 上限（1240 页宽双栏
   从约 32px 降到约 24px）。
