# 漫画生成功能升级思路：接入 handraw-style 风格库

> 状态：**只做思路梳理，尚未动代码，等指令再开工**
> 参考项目：[yang0/handraw-style](https://github.com/yang0/handraw-style)（MIT，v1.8.5）
> 本文关于 handraw-style 的数字/字段均来自实拉仓库核对，不是凭印象。
> **v2 修订（2026-10-10）：目标运行环境改为 16GB 显卡，本机只做开发。多条结论因此改写。**

---

## 0. 两句话结论

**第一句（环境）**：显存从 6GB 提到 16GB 之后，之前"因为 8 步采样救不回结构，所以只能靠垫图"的核心论断**必须重新评估**——
768 / 8 步是 6GB 下的妥协，不是 Qwen-Image 的能力上限。分辨率与步数一放开，
**文本路线（编号 + 名称 + 特征）很可能重新变得有效**，垫图从"唯一出路"降级为"兜底与加强"。

**第二句（资产）**：handraw-style 里对我们有用的三块，优先级是
**主题色（36）→ 画风库（327）→ 分镜节奏（SB-71）**；
它最值得学的工程思想是"**画风还原 = 名称/特征文本 + 编号参考图 + 风格隔离指令，按模型能力分层兜底**"；
它有一块**必须屏蔽**：图文模式（graphic-text），会和"文字一律 PIL 画"的策略正面打架。

## 1. 运行环境（本次修订的核心）

| | 开发机（本机） | 目标机（用户测试） |
|---|---|---|
| 显卡 | RTX 2060 **6GB** | **16GB** |
| 用途 | **只做开发与功能正确性验证** | **画质 / 风格还原 / 性能的唯一判据** |
| 定位 | 跑得通、接口对、不崩 | 出图好不好看、画风像不像、一本漫画要多久 |

> 🔴 **由此产生一条铁律：本机的出图结果不能作为画质与风格还原的判据。**
> 8 步 + 768 + lowvram 出来的画面，只能用来判断"结构没崩、拼装没问题"，
> 不能用来下"这个画风不行"的结论。
> **凡涉及画风还原度的结论，一律以 16GB 机器实测 + 用户反馈为准。**

### 1.1 16GB 能解锁什么（对比 6GB 时代的妥协）

| 项 | 现在（6GB 妥协） | 16GB 可放开 | 对本次需求的意义 |
|---|---|---|---|
| 分辨率 | 768×768 | **1024 ~ 1536**（Qwen-Image 训练分辨率区间） | 分镜格内细节、脸部像素占比大幅改善 |
| 步数 | **8 步** | **20 ~ 30 步**（官方推荐 20–50） | ⭐ 风格词能否生效的关键变量 |
| CFG | 融合路径强制 **CFG=1**（负面词失效） | txt2img 路径可用正常 CFG（7 左右） | 负面提示词**重新生效**，"禁字 / 禁畸形"不再白写 |
| 文本编码器 | 必须放 **CPU** | 可放 GPU | 速度明显提升，AI 步骤不再那么煎熬 |
| 显存策略 | `--lowvram` + `LOW_VRAM=true` | 可关 | 换页开销消失 |
| 批量 | `MAX_BATCH=1` | **batch 2–4** | ⭐ 一次出多张候选给人挑，漫画场景非常实用 |
| 量化 | Q4_K_M（省显存） | Q6_K / Q8_0 / fp8 可选 | 画质与风格保真度整体上移 |
| 整页多格直出 | 基本不可行 | **值得认真试** | handraw 的 SB-* 从"玩具"变成"选项" |

### 1.2 由此引出的基础工程改动（比接风格库更靠前）

现在 `width / height / steps / guidance` 是**建项目时写死的 768 / 768 / 8 / 4.0**（前端硬编码 + `.env` 默认值）。
两套硬件要用同一份代码，就必须把它们变成**可切换的"生成档位"**：

- 「开发档」768 / 8 步 / lowvram —— 本机跑得动
- 「目标档」1024+ / 20+ 步 / 正常 CFG —— 16GB 用
- 项目级可选：分辨率、步数、CFG、批次数、是否垫图

> 这件事不做，风格库接得再好也会被 8 步采样拖死在 6GB 的水平上。
> **建议把"生成档位化"列为 P0 的第一件事，排在主题色之前。**

### 1.3 需要顺带重算的既有参数

- **PDF 导出 DPI**：现在是 `页宽 / 210mm`（1240px → 约 150dpi）。页宽变大后 DPI 变高、PDF 体积变大，要重定上限。
- **气泡字号**：现系数 0.042 + 26px 上限，是按 768 页宽调的，页宽变了要跟着走。
- **`INFER_TIMEOUT_SECONDS=2400`**：16GB + 20 步未必更慢（省掉 lowvram 换页），但要实测重定。
- **`MAX_PIXELS=2073600`**：卡在 1440² 附近，要确认是否放开到 1536²。
- **绿色包体量**：若换 Q6_K / Q8_0，模型体积大增（Q8 可能到 20GB+），下载脚本与包体说明要重写。

## 4. 三块可借 + 一块必须屏蔽

### 4.1 画风库（327）——价值高，路线要按新环境重排

现在的 5 个画风是"手写一行英文"，换成 327 编号体系后前端体验完全不同：分组筛选、缩略图网格、编号可记可分享可复现。

**唯一硬伤**：`traits` 字段**只有中文**（`generation_name` 和 `reference` 是英文）。

- 6GB 时代结论：中文 traits 拼进英文提示词是灾难，8 步模型对风格词根本不敏感 → **只能靠垫图**。
- **16GB 时代结论（修订）**：分辨率 1024+、步数 20–30 之后，风格词生效概率大幅提高，
  "编号 + 生成名 + 参考作者 + traits"这套文本就有机会真正起作用。
  → **文本路线要重新做对照实验，不要预设它没用。**

建议双轨：

1. **主轨 · 文本**：走 handraw 的 `name_activation` 思路——名称足够强的风格只写作者名 + 生成名；
   否则补上 traits（中文 traits 可直接用，或我们补一份英文摘要，**标注为机器翻译、可人工改**）。
2. **兜底轨 · 垫图**：文本效果不达标时，挂编号参考图 + 隔离指令（见 4.1.1）。

#### 4.1.1 垫图机制（从"唯一出路"降级为"兜底与加强"）

handraw 的原文机制：

> 按模型标定 `name_activation`：**strong** → 只写作者名 + 风格名，什么都不加；
> 否则写 traits；**再不行 → 必须垫那张编号参考图**，并注入风格隔离指令。

隔离指令原样抄（别改写）：

```
所附图片仅用于参考画风。只提取参考图的风格特征，例如线条、笔触、媒介、材质、色彩倾向和整体视觉语言；
不要使用、复制或延续参考图中的任何主体、人物、动物、服装、道具、动作、姿态、场景、背景、构图、布局、文字或故事。
最终画面内容完全以用户提供的主题为准。
```

我们的垫图通路本来就是通的（`TextEncodeQwenImage21` 多参考图），所以技术上只是"多挂一张 + 多写一句"。
但有 4 个冲突必须先解决（见第 6 节）。

### 4.2 分镜/排版机制（165，重点是 SB-71）——本项因 16GB 而上调优先级

**先分清两件完全不同的事，否则一定做错：**

| | 我们现在的 layout | handraw 的 SB-xxx |
|---|---|---|
| 作用阶段 | **排版**（PIL 切格拼页） | **生成**（写给模型的版面语言） |
| 内容 | 一页切几格（1×2 / 2×2 / 3×3） | 阅读顺序、大小格、破框、跨格、正反打、特写链… |
| 前提 | 逐格出图，后拼 | **模型一次画一整页 4~9 格漫画** |
| 例 | `grid_2x2` | `SB-002 四格起承转合`、`SB-013 破框构图`、`SB-021 眼睛特写链` |

- **6GB 结论**：整页多格直出几乎必崩，SB 只能当"节奏模板"轻量用。
- **16GB 结论（修订）**：1024–1536 分辨率下，**整页多格直出从"玩具"变成值得认真评估的选项**。
  但"格内人物一致性"仍是硬骨头（每格相当于一次独立生成，一致性靠模型自身的空间连贯性），
  所以定位仍是"**可选玩法 + 特定场景**"，不替换主通路。
- **轻量用法（稳，建议先做）**：把 SB 当**分镜节奏模板**——选一个编号，只取它的节奏与阅读顺序语义，
  决定这一页的格数、大小格分布、镜头序列（SB-021「眼睛特写链」→ 本页 3 个近景/特写格）。
  走现有逐格通路，出图方式一行不改。

> ⚠️ SB-71 里有一批（跨格人物 / 跨格背景 / 破框 / 一镜到底）**强依赖整页画布**，
> 逐格通路里只能降级成"景别 + 构图"近似，界面上要标注"降级可用"。

### 4.3 主题色（36）——收益最大、风险最小

- 注入成本 = **一行文本**（`主题色：克莱因蓝（Klein Blue）。` / `Theme color: Klein Blue.`）
- 不加参考图、不改出图结构、显存零压力（16GB 就更是无所谓）
- **还能外溢到排版阶段**：气泡底色/描边、页码、页边框现在全是硬编码，跟着主题色走之后整本立刻成套
- 建议支持"主色 + 点缀色"两色（handraw 说数量不设死限，我们简化为 1~2 色）

### 4.4 必须屏蔽的一块：图文模式（graphic-text）🔴

handraw 的 `graphic-text` 后缀大意是"文字参与构图、图文一体"，服务**题图 / 社媒卡 / 信息图**。
我们的漫画策略恰恰相反：**文字一律 PIL 画，提示词里明确禁字**（`PANEL_NEGATIVE_EXTRA` 有 `text, letters, words, speech bubble`）。

两者**直接冲突**，注入就是"模型先写一遍字，我们后面再叠一遍"。

> **结论：只借「画风 / 主题色 / 分镜节奏」三块，`graphic-text` 后缀一律不注入。**
> 这条要写进代码注释，防止以后有人"顺手补上"。

## 5. 落地设计

### 5.1 数据层

落 `backend/app/style_library/`：

```
style_library/
├── styles.json            # 327 条（照抄，记录来源版本 1.8.5）
├── layouts.json           # 165 条
├── colors.json            # 36 条
├── style_alias_map.json   # 旧 001-327 ↔ 新 FA-xxx
├── model_capabilities.json
├── traits_en.json         # 【新增，我们自己的】327 条 traits 的英文摘要（机器译 + 可人工修）
├── layouts/SB-001.md …    # 71 份中文正本
└── thumbs/FA-001.webp …   # 327 张缩略图，长边 ~360px，合计约 4–6 MB
```

- **编号体系**：用新的 `FA-xxx`（自带 8 大类，前端好做分组筛选），旧 `001-327` 走别名查询。
- **存量兼容**：老 `project.style` 的 5 个值在新库里做**别名条目**，存量项目零迁移。
- **缩略图进不进 git**：建议**不进**（`.gitignore`），用 `scripts/fetch_style_library.py` 一次性抓取 + 校验，
  绿色包构建时一并打进包。理由：主仓库只有 2.2 MB，塞 5 MB 第三方图片不划算。
- **署名**：画风库页面底部 + 关于页写明来源（yang0 / 原仓库地址 / 版本号）。

### 5.2 服务层（只列接口，不写实现）

| 新增 | 作用 |
|---|---|
| `style_library.load()` | 单例加载各 JSON |
| `style.resolve(key)` | 兼容 老key / `FA-xxx` / `001` / 中文名 |
| `style.expand(key, model_caps)` | → `(cn_label, en_label, traits, ref_image_path, activation_mode)` |
| `rhythm.build(sb_id, page, panel_index)` | 从 SB 编号推导每页格数 / 景别序列 |
| `profile.resolve(name)` | **生成档位**（开发档 / 目标档）→ 分辨率 / 步数 / CFG / batch / lowvram |

- `build_prompt` / `build_scene_prompt` / `build_character_prompt` 的"画风位"统一改调 `style.expand()`，
  由它决定**注入什么文本、是否挂风格参考图**。
- 增量迁移（走 `db.py` 的"缺列才 ALTER"口径）：
  `comic_projects` + `theme_color TEXT`、+ `theme_color2 TEXT`、+ `style_ref_enabled INTEGER DEFAULT 0`、+ `rhythm_template TEXT`、+ `profile TEXT`
- `presets()` API 增补风格库树（分组 + 分页 + 搜索），**别一次把 327 条吐给前端**。
- 🔴 风格 / 主题色只进 `last_prompt`，**绝不回写 `prompt`**（踩过的老坑）。

### 5.3 垫图（画风参考图）——兜底与加强，分期推进

技术上只是"多挂一张 + 多写一句"，但有 4 个冲突必须解决：

1. **slot 编号重排**：现在 `image_1` = 场景图、`image_2..` = 立绘。加风格图必须重排，
   并同步更新提示词里的 `image_N` 指代（`build_prompt` 已参数化，改动可控但必须测）。
2. **CFG 与负面词**：2.1 官方编辑路径是 CFG=1（负面词不生效）→ 隔离指令**必须写正向**。
   16GB 下可另起 txt2img + 正常 CFG 通路做对比，看哪条更划算。
3. **互相污染**：风格图（手绘）+ 场景概念图 + 角色立绘三张一起垫会不会打架？
   → 必须先做**同种子开关对照**再决定。
4. **分期启用**：先在「角色立绘」「场景概念图」上开（单图、结构简单、收益最直接），分镜融合最后再开。

> 备选：不动主通路，单独做「补画风」按钮——先按现有方式出图，再用风格参考图走一次 img2img 转画风。
> 16GB 下多跑一次采样的代价可以接受。

### 5.4 交互层

- **新建项目**：画风选择器（分组 + 搜索 + 缩略图网格），现有 5 个画风做成"常用"置顶；**生成档位选择**（开发档 / 目标档）
- **项目设置**：主题色（36 色卡，1~2 色）、分镜节奏模板（SB-71 选一，可空）、分辨率 / 步数 / CFG
- **分镜步骤**：每页顶部显示当前节奏模板名，可随时换
- 🔴 **别让本地 8B 模型参与"327 选 1"**（1.8 秒/字，又慢又容易乱）→ 选择放前端；
  要做推荐就用**前端本地关键词打分**（零成本、零延迟）
- 前端缓存机制已有（`/static` no-cache + `?v=mtime` 指纹），新增 js 走同一套即可

## 6. 关键风险与坑（逐条）

| # | 坑 | 对策 |
|---|---|---|
| 1 | `traits` 只有中文 | 补一份英文摘要（`traits_en.json`，标注机器译）；或纯保留中文做展示 |
| 2 | 垫图 slot 冲突 + CFG=1 负面失效 | 重排 slot；隔离指令写**正向** |
| 3 | 风格图 / 场景图 / 立绘 三图互相污染 | 先做同种子开关对照实验，再分期启用 |
| 4 | `graphic-text` 与禁字策略冲突 | 明确禁用，写进注释 |
| 5 | 整页多格直出的一致性 | 16GB 下可试，但定位为"可选玩法"，不替换主通路 |
| 6 | **本机 6GB 结果被误当画质判据** | 铁律：本机只验功能正确性，画质一律以 16GB 机为准 |

## 8. 待你拍板的 7 个问题

1. **目标档基线**：16GB 下分辨率 / 步数定多少？（建议 1024×1024 / 24 步先试，再看 1280）
2. **量化档位**：继续 Q4_K_M，还是换 Q6_K / Q8_0 / fp8？（画质提升 vs 包体与下载量）
3. **批量候选**：要不要开 batch 2–4 一次出多张候选给人挑？（很实用，但每格机时翻倍）
4. **画风库范围**：全量 327，还是先挑 30–60 个精选？（全量对前端与选择体验都是负担）
5. **编号体系 / 缩略图**：新 `FA-xxx` 还是旧 `001-327`？缩略图不进 git（脚本抓取 + 进绿色包）可以吗？
6. **垫图对照实验**：做不做？16GB 机器上要真实出图若干张，需要你配合跑。
7. **SB 分镜**：只做"节奏模板"（稳），还是也要"整页直出"评估（16GB 下可能出惊喜）？
